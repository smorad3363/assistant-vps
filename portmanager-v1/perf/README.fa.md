# ابزار عیب‌یابی مصرف CPU در Port Manager V1

**نسخه اصلی V1 دست‌نخورده است.** این پوشه ابزار آزمایشی **فقط‌خواندنی**
ارائه می‌کند و نصب‌کنندهٔ اصلی، `/usr/local/bin/portmanager`، قوانین
`iptables`، کران‌جاب‌ها یا تنظیمات `tc` را تغییر نمی‌دهد.

## علت فشار CPU

در سورس V1، `liverows()` در **هر دور** `ensure_rules()` را فراخوانی می‌کند.
این تابع با `ss` و `iptables-save/ip6tables-save` پورت کشف می‌کند،
`iptables -N`, `-C` و `-S` را بررسی و در صورت تغییر فهرست پورت‌ها
زنجیرهٔ حسابداری را با `-F` و سپس قواعد متعدد `-A` بازسازی می‌کند.
دریافت دو snapshot، اجرای چند `awk`، `sort` و `clear` نیز در
چرخهٔ یک‌ثانیه‌ای تکرار می‌شود.

**بار CPU در `ksoftirqd` ممکن است از تعداد قوانین `mangle` و نرخ
پکت شبکه باشد؛ خاموش کردن نمایشگر الزاماً بار packet path را حذف نمی‌کند.**
اثر دقیق باید قبل/بعد با `top`/`pidstat` و نرخ PPS بررسی شود.

## اقدامات فوری بدون تغییر قوانین

1. با `Ctrl+C` از Live خارج شوید. از `portmanager live 1` استفاده
   نکنید؛ فعلاً `portmanager live 5` یا بیشتر و ترجیحاً در ساعات خلوت.
2. تعداد پورت‌های مانیتورشده و قواعد حسابداری را فقط بخوانید:

```bash
sudo wc -l /etc/portmanager/ports.conf
sudo iptables -t mangle -S PORTMANAGER_ACCT | wc -l
sudo ip6tables -t mangle -S PORTMANAGER_ACCT | wc -l
ps -eo pid,ppid,pcpu,pmem,comm,args --sort=-pcpu | head -20
cat /proc/softirqs | grep -E 'NET_RX|NET_TX'
```

3. اگر CPU بدون پنجره مانیتور هم بالا بود، بررسی packet rate و
   تعداد قوانین را در اولویت بگذارید. **با `iptables -F` یا
   `tc qdisc del` سرور فعال را دستکاری نکنید.**

## نمایشگر جداگانه و سبک‌تر (اختیاری)

این ابزار به جای `ensure_rules` در هر دور، فقط خروجی خواندنی
`iptables-save -c -t mangle` را از زنجیره موجود V1 می‌خواند؛
هیچ محدودیت سرعت جدیدی اعمال نمی‌کند و برای یک سرور با قواعد بسیار
زیاد هم هزینه نمونه‌گیری باید اندازه‌گیری شود.

پس از clone شاخه توسعه روی یک VM موقت:

```bash
sudo python3 portmanager-v1/perf/fast_live.py --interval 5 --top 20
sudo python3 portmanager-v1/perf/fast_live.py --interval 10 --once
python3 -m unittest discover -s portmanager-v1/perf -p 'test_*.py'
```

`--interval` حداقل ۲ ثانیه است؛ اما ابزار اگر بیش از ۱۰۰۰ قانون
ببیند، فاصله را خودکار حداقل ۱۰ ثانیه و برای بیش از ۸۰۰۰ قانون حداقل
۳۰ ثانیه می‌کند. اگر خواندن شمارنده‌ها کند باشد، فاصله متناسب با هزینهٔ
واقعی بالاتر می‌رود. سرعت‌ها از اختلاف
شمارنده‌های بسته/بایت زنجیره قدیمی محاسبه می‌شوند و ممکن است با
payload کاربردی یکسان نباشند. راه‌حل بلندمدت کاهش تعداد قواعد،
برداشتن `ensure_rules` از حلقه Live و گزارش‌گیری تجمیعی است.

## گزارش باگ برای توسعه‌دهنده

خروجی `wc -l`، خلاصه `top`/پردازش‌های `ksoftirqd`,
پهنای‌باند شبکه، حالت IPv4/IPv6 و نتیجهٔ مصرف CPU **قبل و بعد**
از بستن Live را ثبت کنید. IP و اطلاعات کاربری را در گزارش عمومی
ناشناس‌سازی کنید.
